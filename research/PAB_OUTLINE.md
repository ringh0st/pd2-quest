# PAB (Salesforce Certified Platform App Builder) lesson outline

Exam guide: https://help.salesforce.com/s/articleView?id=005298964&type=1&language=en_US (read 2026-11-16).
60 scored questions + up to 5 unscored, 105 min, 73% to pass, aligned to the **Summer '26** release.

Objective codes below: `fund-1..5`, `data-1..4`, `logic-1..8`, `ui-1..5`, `deploy-1..4`, numbered in the order of `src/data/pab/exam.json`.

Key-fact markers: **[read]** = I read this on the cited page on 2026-11-16. **[check]** = standard fact, not re-read this session; open the URL before writing a question on it.

Help URLs use the form `https://help.salesforce.com/s/articleView?id=<id>&type=5`; below, `HELP:<id>` is short for that URL. Trailhead unit URLs are given in full.

> **Version trap for question writers.** The exam is Summer '26, but the Help pages read on 2026-11-16 are newer. Things that changed or are new there: Flow Builder's **Test Mode** replaces Debug for autolaunched and record-triggered flows; **DevOps Center** is now **Lifecycle Center**; Agentforce-assisted flow troubleshooting and test generation are **beta**; and the roll-up summary article now mentions lookup fields. Don't write questions that depend on these, or give both old and new names. The marketplace is called **AgentExchange** (formerly AppExchange) in the exam guide itself, so use that name.

**Key facts**
- fund-1: Declarative first. A before-save record-triggered flow updates the triggering record about **10 times faster** than a record-change process and supports only **Assignment, Decision, Get Records and Loop** elements; for values set only after save (Id, Last Modified Date), related records or other actions, use an after-save flow or Apex after trigger. [read] HELP:platform.flow_concepts_trigger_record.htm
- fund-1: Typical code-only needs: Apex managed sharing when sharing rules and manual sharing can't express the rule (custom objects only; only users with Modify All Data can change it), and custom Lightning components when standard components don't fit. [read] HELP:platform.security_data_access.htm, HELP:platform.lightning_app_builder_mobile_guidance.htm
- fund-2: AgentExchange solution types: **apps** (packaged objects, tabs, components), **components** (building blocks, mostly from partners), **Bolt solutions** (industry solutions; deployment needs the partner's services), **flow solutions** (flow actions and flow templates), plus consultants. [read] https://trailhead.salesforce.com/content/learn/modules/appexchange-solutions/tour-solutions-by-type
- fund-2: Try before you buy: a **test drive** is a read-only Developer Edition org from the provider; a **Trialforce trial** is a writable Developer Edition org for a limited time that you can keep if you buy; or try it in your sandbox. Never install in production without testing in a sandbox or Developer Edition org first. Install for **Admins Only, All Users or Specific Profiles** (unsure: Admins Only). [read] https://trailhead.salesforce.com/content/learn/modules/appexchange_basics/appexchange_basics_listings, https://trailhead.salesforce.com/content/learn/modules/appexchange_basics/appexchange_basics_install
- fund-3: Object permissions and field-level security live in **permission sets, permission set groups and profiles**. A user has **exactly one profile** and can have many permission sets. Salesforce recommends granting access with permission sets and groups, starting from **Minimum Access - Salesforce** (or a clone). Standard profiles' object permissions can't be edited (clone instead). [read] HELP:platform.security_data_access.htm; https://trailhead.salesforce.com/content/learn/modules/data_security/data_security_objects
- fund-3: Field-level security hides a field everywhere (related lists, list views, reports, search); page layouts only control detail and edit pages, so FLS is the only real protection for a field. [read] HELP:platform.security_data_access.htm
- fund-3: A **muting permission set** inside a permission set group turns off selected permissions for that group's users. [read] HELP:platform.perm_set_groups.htm
- fund-4: Org-wide defaults: **Private, Public Read Only, Public Read/Write**, plus **Controlled by Parent**; **Public Read/Write/Transfer** only for cases and leads; Public Full Access and View Only only for specific objects. Set OWDs to the most restrictive level needed, then open up; other sharing tools **only grant more access, never less**. Internal and external OWDs can differ. [read] HELP:platform.security_sharing_owd_about.htm, HELP:platform.sharing_model_fields.htm
- fund-4: The role hierarchy gives users above the owner the same access to the owner's records; roles control record access, profiles and permission sets control object and field access. [read] HELP:platform.security_data_access.htm
- fund-5: Sharing rule types: **owner-based**, **criteria-based** (text criteria are **case-sensitive**; supported field types include checkbox, date, number, picklist, text, lookup to user/queue) and **guest user** rules (the only way to share with unauthenticated guests). Manual sharing is done by record owners; user sharing hides or shows users to each other. [read] HELP:platform.security_sharing_rule_types.htm, HELP:platform.security_data_access.htm
- fund-5: Teams (account, opportunity, case teams) and territory hierarchy also grant access. [check] HELP:platform.security_data_access.htm (territories read; teams not detailed on that page)
- fund-6: **Restriction rules** filter records a user already has access to (list views, lookups, related lists, reports, search, SOQL/SOSL). Available for custom objects, external objects, quotes, contracts, events, tasks, time sheets and time sheet entries; **2 active rules per object** in Enterprise and Developer, **5** in Performance and Unlimited. Configure so only one active rule applies to a user. **Scoping rules** only change which records users see by default; they don't remove access. [read] HELP:platform.security_restriction_rule.htm, HELP:platform.security_data_access.htm
- fund-7: Report formats: **tabular** (default; a list), **summary** (group rows, subtotals, charts; the workhorse), **matrix** (group rows and columns), and joined. A dashboard component can't use a **joined** or **historical trend** report as its source. A tabular report can feed a dashboard only if you limit its rows. [read] https://trailhead.salesforce.com/content/learn/modules/lex_implementation_reports_dashboards/lex_implementation_reports_dashboards_report_formats, .../lex_implementation_reports_dashboards_visualizing_data
- fund-7: Custom report types: a primary object plus up to **4 object relationships** (levels); **60 object references** in total; up to **1,000 fields**; a report with columns from more than **20 objects** errors. Names up to 50 characters. Multilevel master-detail objects need **Allow Reports** to be used. [read] HELP:analytics.reports_report_type_guidelines.htm, HELP:platform.relationships_considerations.htm
- fund-8: A dashboard's **running user** decides what data every viewer sees. A **dynamic dashboard** runs as the logged-in viewer; limits **5** (Enterprise), **10** (Unlimited, Performance), **3** (Developer); can't be in a private folder, can't have scheduled refreshes, can't be subscribed to; deleted ones in the Recycle Bin still count. Needs **Manage Dynamic Dashboards**. [read] HELP:analytics.dashboards_dynamic_overview.htm

## Data Modeling and Management (20%): 9 lessons

| # | Lesson | Objectives |
|---|---|---|
| data-1 | Objects, fields and Schema Builder: choosing the data model | data-1 |
| data-2 | Lookup or master-detail? | data-2 |
| data-3 | Many-to-many: junction objects | data-1, data-2 |
| data-4 | Hierarchical, external and indirect lookups | data-2, data-4 |
| data-5 | What a relationship changes: access, UI and reports | data-2 |
| data-6 | Picking field types and picklists | data-3 |
| data-7 | Changing a field's type without losing data | data-3 |
| data-8 | Importing and exporting data | data-4 |
| data-9 | External data with Salesforce Connect | data-4 |

**Key facts**
- data-1: Object types: standard, custom, external, platform events, big objects. Schema Builder can create objects, fields (including relationship and formula fields) and shows the model; dragging objects around the canvas changes nothing. [read] https://trailhead.salesforce.com/content/learn/modules/data_modeling/objects_intro, .../schema_builder
- data-1: Custom fields per object: Professional **100**, Enterprise **500**, Unlimited/Performance **800**, Developer **500** (Group 100, Contact Manager 25, Personal 5). Hard limit **800** (900 for some objects such as Account, Contact, Case, custom objects) with managed-package fields. A geolocation field counts as **3** fields, a custom address field as **9**. [read] HELP:platform.custom_field_allocations.htm
- data-2: Master-detail: deleting the master deletes the details (and undeleting it restores them); details have **no Owner field** (owner = master's owner), so a custom detail object can't have sharing rules, manual sharing or queues; details inherit the master's security; the relationship field is **required** on the detail layout; reparenting is off by default (**Allow reparenting**). Each custom object: **2 master-detail** and **40 relationships** in total; best practice at most **10,000** children per master. [read] HELP:platform.overview_of_custom_object_relationships.htm
- data-2: You can't create a master-detail field on an object that **already has data**: create a lookup, fill it on every record, then convert. Standard objects can't be the detail of a custom object. Up to **3 custom detail levels**. A custom object on the master side can't be deleted; deleting the detail object converts the relationship to a lookup. [read] HELP:platform.relationships_considerations.htm
- data-2: Lookup: optional or required; if optional, on parent delete choose **Clear the value** (default), **Don't allow deletion**, or **Delete this record also** (custom objects only; cascade-delete is **off by default** and must be enabled by Salesforce; it bypasses security). Lookups don't support roll-up summaries or inherited sharing. A self-relationship must be a lookup. [read] HELP:platform.overview_of_custom_object_relationships.htm, HELP:platform.relationships_considerations.htm
- data-3: Many-to-many = a **junction object** with **two master-detail** fields. The **first** one created is the **primary** (look and feel, owner, division); deleting it makes the secondary primary. A junction record is deleted if either master is deleted. Access to a junction record needs access to **both** masters. You can't delete a parent with more than **200** junction records if the junction has a roll-up to the other parent. A junction object can't be a master in a multilevel relationship, and the two masters can't be the same object. Roll-ups from the junction can be created on both masters. [read] HELP:platform.relationships_considerations.htm
- data-4: **Hierarchical** relationships exist **only on the User object** (e.g. a manager field). **External lookup**: child (standard, custom or external) → parent **external object**, matched on the parent's External ID. **Indirect lookup**: child **external object** → parent standard/custom object, matched on a custom **unique, external ID** field of the parent. [read] HELP:platform.overview_of_custom_object_relationships.htm
- data-5: Relationship choice changes record access (master-detail detail inherits sharing; lookup doesn't), the UI (required field, related lists) and reporting (custom report types follow relationships). Converting master-detail → lookup sets the detail's OWD to **Public Read/Write**; lookup → master-detail sets it to **Controlled by Parent** and needs a value in every record. You can't convert master-detail → lookup if the master has **roll-up summary fields**. [read] HELP:platform.relationships_considerations.htm, HELP:platform.notes_on_changing_custom_field_types.htm
- data-6: Picklists: a **global value set** shares values across fields; a **restricted picklist** blocks values not in the set (even through the API); a **dependent picklist** is filtered by a controlling picklist or checkbox; multi-select picklists need `includes`/`contains` in reports and have lower value limits. Record types use subsets of the **master picklist**. [read] https://trailhead.salesforce.com/content/learn/modules/picklist_admin/picklist_admin_start, .../picklist_admin_global; HELP:platform.creating_record_types.htm
- data-6: Long and rich text area: default **32,768** characters, max **131,072**, min **256**; **1,638,400** characters per object across these fields. Auto number max **30** characters. [read] HELP:platform.custom_field_allocations.htm, HELP:platform.notes_on_changing_custom_field_types.htm
- data-7: Changes that can **lose data**: to or from Date or Date/Time; to Number, Percent or Currency from any type; from Checkbox; from multi-select picklist; to multi-select picklist (values not in the definition are dropped); from Auto Number; to Auto Number except from Text; Text → Picklist; Long Text Area → anything except Email, Phone, Text, Text Area or URL (truncated to **255**). Lost data deletes list views based on the field. [read] HELP:platform.notes_on_changing_custom_field_types.htm
- data-7: Not allowed: converting **to or from a formula** field; changing a field mapped for **lead conversion**; changing a field referenced by Apex, Visualforce, processes or flows; encrypted fields. Rich text area converts only to long text area. Picklist → checkbox lets you map values. An External ID stays one only as text, number or email. [read] same URL
- data-8: Tools: **Data Import Wizard** (in-browser, up to **50,000** records, imports accounts, contacts, leads, solutions, campaign members and custom objects; **no export**); **Data Loader** (client app, up to **5 million** records, insert/update/upsert/delete/export, command line on Windows only, Enterprise/Unlimited/Performance/Developer). The import wizard **can't import** assets, cases, campaigns, contracts, documents, **opportunities** or products. Import file up to **100 MB**, up to **90 fields** per record. [read] HELP:xcloud.import_which_data_import_tool.htm, HELP:xcloud.data_loader_about.htm, HELP:xcloud.import_limits.htm
- data-8: Duplicate management (matching and duplicate rules) keeps imports clean; it's in the trailmix's data section. [check] https://trailhead.salesforce.com/content/learn/modules/sales_admin_duplicate_management
- data-9: **Salesforce Connect** maps **external objects** to tables in an external system and reads data **in real time, without copying it**. Use it for large data you don't want to store, small amounts at a time, and real-time needs. External objects work with global search, lookups, feeds, the mobile app, SOQL/SOSL, Apex, change sets and packages. **Read-only by default**; writable if the data source allows. Included in Developer Edition, **extra cost** in Enterprise, Performance and Unlimited. [read] HELP:platform.platform_connect_about.htm
- data-9: **External Services** registers an OpenAPI (REST) spec and turns its operations into invocable actions for Flow, without code. [read] https://trailhead.salesforce.com/content/learn/modules/external-services

## Business Logic and Process Automation (32%): 11 lessons

| # | Lesson | Objectives |
|---|---|---|
| logic-1 | Formula fields and their limits | logic-1 |
| logic-2 | Cross-object formulas | logic-1 |
| logic-3 | Roll-up summary fields | logic-2 |
| logic-4 | Validation rules | logic-3 |
| logic-5 | Choosing the right flow type | logic-6 |
| logic-6 | Record-triggered flows: before save or after save | logic-4, logic-6 |
| logic-7 | Screen flows and where to put them | logic-4, logic-6 |
| logic-8 | Scheduled and autolaunched flows, subflows | logic-4, logic-6 |
| logic-9 | Flow Approval processes | logic-5 |
| logic-10 | Maintain, monitor and troubleshoot flows | logic-7 |
| logic-11 | Agentforce for business automation | logic-8 |

**Key facts**
- logic-1: Formula fields: up to **3,900 characters**; **1,300** displayed characters after evaluation; save size and compile size each at most **15,000 bytes** (TEXT, DATEVALUE, DATETIMEVALUE, DATE grow compile size). Formulas can't use long text area, encrypted or Description fields; you can't delete a field referenced in a formula. [read] HELP:platform.formula_field_limits.htm
- logic-1: Formula fields are read-only and calculated; formula return types (checkbox, currency, date, date/time, number, percent, text, time). [check] HELP:platform.choosing_a_formula_data_type.htm
- logic-2: Cross-object formulas: at most **10 unique relationships per object**, counted across all formulas, rules and lookup filters (two formulas on the same opportunity → account path count once). Cross-object formulas **can't be used in roll-up summaries**; activities can't reference related contact/account merge fields; polymorphic Owner needs `Owner:User.` or `Owner:Queue.`; Name fields built from other fields (e.g. `Owner.Name`) can't be used. [read] HELP:platform.fields_creating_cross_object_notes.htm
- logic-3: Roll-up summary: **COUNT, SUM, MIN, MAX** of detail records. SUM: number, currency, percent; MIN/MAX also date and date/time. Allowed on any custom master of a master-detail; a standard master of a custom detail; **Opportunity** from opportunity products; **Account** from opportunities; **Campaign** from campaign members. Can't aggregate auto number fields, cross-object formulas, or formulas using NOW/TODAY/DATEVALUE. Recalculation can take up to **30 minutes**; mass recalculation doesn't fire workflow or validation. After creating one, you **can't convert** the master-detail to a lookup or change the detail object. **25** roll-up summary fields per object. [read] HELP:platform.fields_about_roll_up_summary_fields.htm, HELP:platform.custom_field_allocations.htm (raising 25 toward 40 via Support: [check])
- logic-3: Roll-ups aren't shown on edit pages, so they can be used in validation rules but not as the error location; enforce "max 25 children" with a validation rule on the child, e.g. `AND(ISNEW(), Parent.Line_Count__c >= 25)`. FLS-hidden detail fields still count. [read] same URL
- logic-4: A validation rule's formula returns **TRUE when data is invalid**, then shows an error at the **top of the page or next to a field**. Rules apply to UI, API and imports, even for fields not on the layout, but **not** to Quick Create. Use `ISNEW()`, `ISCHANGED()` and `PRIORVALUE()` to fire only when needed; bypass for chosen users with a **custom permission** in a permission set (`$Permission`). [read] HELP:platform.fields_about_field_validation.htm, https://trailhead.salesforce.com/content/learn/modules/validation-rules/implement-best-practices, .../bypass-your-validation-rules
- logic-4: In the save order, validation rules run after before-save flows and before triggers. [check] https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_triggers_order_of_execution.htm
- logic-5: Core flow types: **Screen Flow** (user interaction; no Wait elements); **Record-Triggered Flow** (before save, after save, before delete); **Schedule-Triggered Flow** (runs for a batch of records at a time and frequency; no screens); **Platform Event-Triggered Flow**; **Autolaunched No Trigger** (from Apex, REST, buttons/links, subflows; no screens); **Flow Approval Process** (autolaunched or record-triggered); **Orchestration**. Only a record-triggered flow can use the **Custom Error** element; only a screen flow can use **Choice** resources. [read] HELP:platform.flow_concepts_type.htm
- logic-6: Before-save: only Assignment, Decision, Get Records and Loop; changes `$Record` directly (no Update Records needed); runs **immediately before Apex before triggers**. After-save: can change **related records** and run actions; has access to the Id and system fields. Before-delete runs when a record is flagged for deletion. Per-org: **50 versions** per flow; **2,000 active** and **4,000 total** flows per flow type (Enterprise and above; 5 in Essentials/Professional). [read] HELP:platform.flow_concepts_trigger_record.htm, HELP:platform.flow_concepts_type.htm, HELP:platform.flow_considerations_limit.htm
- logic-7: Screen flows can run from Lightning pages, Experience Builder pages, flow actions (quick actions), utility bar, custom buttons/links, web tabs, Aura and LWC, Visualforce. On a Lightning page the flow starts every time the page loads. Most distribution methods require the **Run Flows** permission. [read] HELP:platform.flow_concepts_type.htm, https://trailhead.salesforce.com/content/learn/modules/screen_flow_distribution
- logic-8: Schedule-triggered flows run once, daily or weekly; one interview per record in `$Record`; at most **250,000 interviews per 24 hours or 200 × user licenses**, whichever is greater; monitor them in **Scheduled Jobs**. Flow interview size about **1 MB**; heap per interview **215 MB** (API 61.0+). [read] HELP:platform.flow_concepts_trigger_schedule.htm, HELP:platform.flow_considerations_limit.htm
- logic-8: Subflows let one flow call another; flows run inside a transaction and the whole transaction rolls back on failure; per-transaction limits apply. [read] HELP:platform.flow_monitor.htm. Per-transaction numbers: [check] HELP:platform.flow_considerations_limit_transaction.htm
- logic-9: **Flow Approval Processes** build multi-step, multi-user approvals in Flow (an approval orchestration). Types: **Autolaunched Flow Approval Process** (launched by Apex, REST API, custom buttons or links; inputs `recordId`, `submitter`, `submissionComments`) and **Record-Triggered After Save Flow Approval Process** (on create or update). Limits: **50 versions** each, **2,000 active**, **4,000 total**. Classic approval processes still exist (Trailhead teaches them for discount approvals). [read] HELP:platform.flow_concepts_type.htm, HELP:platform.automate_automated_approvals_considerations_limit.htm, https://trailhead.salesforce.com/content/learn/modules/business_process_automation
- logic-9: Migration considerations and record locking for flow approvals: [check] HELP:platform.automate_automated_approvals_considerations_migrating_from_legacy_approval_processes.htm, HELP:platform.automate_automated_approvals_concept_record_locking.htm
- logic-10: **Fault paths** handle element errors (e.g. a validation rule blocks Update Records): notify an admin, show a message in a screen flow, or take another action. With no fault path, the default handling applies. Flow error emails go to the **user who last modified the flow** or to **Apex Exception Email Recipients** (Process Automation Settings). [read] HELP:platform.flow_build_logic_fault.htm, HELP:platform.flow_troubleshoot_error_email.htm
- logic-10: **Debug** in Flow Builder runs the flow for real unless you choose **rollback mode**; **debug as another user only in a sandbox**; needs View All Data. Current docs: autolaunched and record-triggered flows use **Test Mode** (saved test scenarios, assertions) instead of Debug; check what applied in Summer '26 before testing this. Monitor paused interviews and scheduled actions in Setup; compare versions and view flow dependencies in the Automation app. [read] HELP:platform.flow_test_debug.htm, HELP:platform.automate_flow_test_mode.htm, HELP:platform.flow_monitor.htm
- logic-11: **Setup with Agentforce**: an admin agent in Setup that creates objects, fields and flows and manages permission sets, groups, OWDs and sharing rules from prompts; it acts **only after you confirm**, only within **your permissions**, and its changes are logged in the **Setup Audit Trail**. [read] https://trailhead.salesforce.com/content/learn/modules/setup-with-agentforce-for-admins/get-started-with-setup-with-agentforce
- logic-11: Agentforce in automation: a **Prompt Template Capability-Triggered Flow** adds data to a prompt template; Agentforce for Flow can generate test scenarios and diagnose flow errors (beta). Agent actions can be built from flows, Apex invocable methods and prompt templates. [read] HELP:platform.flow_concepts_type.htm, HELP:platform.automate_flow_test_mode.htm; agent actions [check] https://developer.salesforce.com/docs/ai/agentforce/guide/agent-invocablemethod.html

| ui-3 | Lightning App Builder and Lightning page types | ui-1, ui-3 |
| ui-4 | Dynamic Forms, visibility rules and dynamic actions | ui-1, ui-3 |

| ui-6 | Quick actions: global vs object-specific | ui-2, ui-5 |

**Key facts**
- ui-1: Lightning apps group tabs and items, and can add a utility bar; build them in App Manager. Tab types: custom object tabs, web tabs, Lightning page tabs, Visualforce tabs. [check] HELP:platform.apps_lightning_create.htm, HELP:platform.custom_tab_overview.htm
- ui-2: A user's page layout comes from **profile + record type**. Record types offer different picklist values, business processes (opportunity, case, lead, solution) and layouts; "Master" is reserved; Professional Edition needs an add-on. If a profile has a single record type, users aren't asked to choose. [read] HELP:platform.creating_record_types.htm
- ui-2: **Compact layouts** drive the highlights: in the mobile app the record highlights show up to **10** fields and expanded lookup cards the first **4**; in Lightning Experience the highlights panel shows up to the first **7**; Outlook/Gmail show **3**. One compact layout per record type; set a primary compact layout per object. [read] HELP:platform.compact_layout_overview.htm
- ui-3: Lightning page types: **App page** (mobile and desktop; supports **only global actions**), **Home page** (Lightning Experience only; assign by app and profile), **Record page** (Lightning Experience and mobile), Email Application Pane, Forecasts, Command Center, Omni Supervisor and Quick Action pages (beta). **A page's type can't be changed** after creation. Actions on Lightning record and Home pages come from the object and global page layouts; App Builder can't add, edit or remove them there. [read] HELP:platform.lightning_page_types.htm
- ui-3: Lightning App Builder vs page layout editor: App Builder customizes Lightning pages only (not Classic); with the **Record Detail** component, field placement still comes from the page layout; only Lightning pages can be assigned by **app** and **form factor**. [read] HELP:platform.lightning_pages_or_page_layouts_when_to_choose.htm
- ui-4: **Dynamic Forms** move fields and sections onto the page as components with **visibility rules** (record data, user, device); fewer page layouts and record types; create/edit/clone use the page's fields, not the layout. Supported for most LWC-enabled objects. [read] HELP:platform.dynamic_forms_overview.htm
- ui-4: **Dynamic actions** let you place and filter actions in App Builder instead of the page layout. [check] HELP:platform.lightning_app_builder_create_dynamic_action.htm
- ui-5: Custom buttons appear to the right of standard buttons; to replace a standard button, define the custom one and swap them on the layout. **Hiding a button doesn't remove access**: use permissions. Visualforce pages used as buttons need the **standard controller** of the same object (list buttons: standard list controller). In the mobile app, **custom links, list-view buttons and OnClick JavaScript buttons aren't available**; URL and Visualforce buttons on the layout are. [read] HELP:platform.links_considerations.htm
- ui-6: **Global actions** live on the global publisher layout, aren't context-aware (no prefilled fields from the page) and create records with **no relationship** to the current record. Create actions for a **master-detail detail object must be object-specific**. **Object-specific actions** create or update records related to the current record (Create, Update, Log a Call, Send Email on cases, custom actions). Visualforce custom actions: object-specific need the standard controller; global ones can't use standard controllers. [read] HELP:platform.actions_overview_global.htm, HELP:platform.actions_overview_object_specific.htm
- ui-6: Predefined field values on actions set defaults for fields on the action layout. [read] https://trailhead.salesforce.com/content/learn/modules/salesforce1_mobile_app/salesforce1_mobile_app_actions_global (objective list)
- ui-7: Custom **Aura** or **LWC** components appear in App Builder only if configured for it (for LWC: `isExposed` and `targets` in the `.js-meta.xml`). Container-like custom components (tabs, accordions) aren't supported in App Builder. Components can be phone-only or desktop-only. [read] HELP:platform.lightning_page_components_custom.htm; meta file details [check] https://developer.salesforce.com/docs/platform/lwc/guide/reference-configuration-tags.html

**Key facts**
- deploy-1: Org development model: develop in **Developer** sandboxes (no production data), integrate in **Developer Pro**, user-acceptance test in **Partial Copy**, train or stage in **Full** (all data); keep changes in **source control** and deploy with a manifest (`package.xml`). Change sets suit simple orgs; source-driven models suit teams. [read] https://trailhead.salesforce.com/content/learn/modules/org-development-model
- deploy-1: **Lifecycle Center (formerly DevOps Center)**: click-based releases backed by source control, with branches managed for you; now agentic and built into the platform. Use "DevOps Center" in questions for the Summer '26 exam, or both names. [read] https://trailhead.salesforce.com/content/learn/modules/devops-center-quick-look/say-hello-to-devops-center
- deploy-2: Refresh interval and storage: **Developer** 1 day, 200 MB data and 200 MB files, metadata only. **Developer Pro** 1 day, 1 GB data and 1 GB files, metadata only. **Partial Copy** 5 days, 5 GB data, files same as production, metadata plus sample data, **sandbox template required**. **Full** 29 days, same storage as production, metadata and all data, template optional. Sandboxes are isolated from production. [read] HELP:platform.data_sandbox_environments.htm
- deploy-2: Sandbox counts per edition (e.g. Enterprise: 25 Developer, 1 Partial Copy) and add-on bundles: the table didn't parse cleanly. [check] same URL
- deploy-3: **Change sets** move metadata (setup changes), **never data**, between orgs affiliated with the same production org (production and its sandboxes) over an authorized **deployment connection**. **Outbound** in the source org, **inbound** in the target; inbound change sets deploy **as a whole**, not component by component. Permissions: Create and Upload Change Sets (outbound); Deploy Change Sets + Modify Metadata Through Metadata API Functions (inbound). [read] HELP:platform.changesets.htm, HELP:platform.changesets_implementation_notes.htm
- deploy-4: Include **every dependent component** (adding only an object deploys it **without its fields**). An uploaded change set can't be changed: **clone** it to add components. Change sets **can't delete or rename** components. Max **10,000 files**. **Validate** to test-deploy first (the org is locked for setup changes meanwhile). Deployment is **one transaction**: all or nothing, and can't be rolled back once done. To production, **all local Apex tests run** if the set includes Apex; not automatically in a sandbox target. Standard objects can't be included (so action overrides on standard objects can't go by change set). Users are matched by username (the sandbox suffix is ignored). [read] HELP:platform.changesets_best_practices.htm, HELP:platform.changesets_implementation_notes.htm
- deploy-5: **Managed** packages: you can't see or change their code/metadata, the provider upgrades them, and their contents **don't count** against your app, tab and object limits; namespace prefix on components. **Unmanaged**: editable, **count** against limits, and to upgrade you **uninstall and reinstall**. [read] https://trailhead.salesforce.com/content/learn/modules/appexchange_basics/appexchange_basics_install, https://trailhead.salesforce.com/content/learn/modules/second-generation-managed-packages
- deploy-6: **Unlocked packages** are for internal use or a specific customer's project; **managed 2GP** is recommended over 1GP for apps you distribute; 2GP is source-driven, built with the Salesforce CLI, and a namespace can't change once set. Installing a package with Apex runs its tests and the org's tests; permission sets in a managed package can't be edited (clone them). [read] https://trailhead.salesforce.com/content/learn/modules/second-generation-managed-packages, HELP:xcloud.distribution_installing_packages.htm
- deploy-7: Plan: build and test in sandboxes, include dependencies and profiles or permission sets, validate first, deploy in low-use hours, plan around maintenance windows, then do post-deploy steps that can't be deployed (data, manual setup). Choose the tool by need: change sets (simple, connected orgs), packages (modular or distributed apps), CLI/Metadata API or DevOps (Lifecycle) Center (source control, teams). [read] HELP:platform.changesets_best_practices.htm, HELP:platform.deploy_sandboxes_intro.htm
